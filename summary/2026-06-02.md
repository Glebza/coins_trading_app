## Carry Formula

Implemented in `framework/forecasts/carry_forecast.py`.

Formula:

```text
raw_carry = (dividend_yield - funding_rate) / annualized_return_volatility
carry_forecast = clip(raw_carry * 30, -20, +20)
```

Important behavior:

- If a share has **no dividends**, `dividend_yield = 0.0`.
- With positive RUONIA, carry becomes negative:

```text
carry_raw = (0.0 - funding_rate) / volatility
```

This is intentional: a non-dividend share has negative carry under the equity carry rule.

Function naming was cleaned up to use verb-style names per `.cursor/rules/code-simplicity.mdc`:

- `calculate_equity_carry_raw(...)`
- `calculate_equity_carry_forecast(...)`
- `calculate_annual_dividend_yield_series(...)`
- `calculate_funding_rate_series(...)`
- `add_carry_forecast_columns(...)`
- `calculate_known_at_series(...)`

  - aggregates per-stage and portfolio diagnostics
- `framework/backtest/__main__.py`

  - prints FDM, forecast correlations, CAGR, and OOS stage summaries

OOS behavior:

```text
start=2022-01-01, end=2026-01-01, step=1y

Stage 1: train 2022       -> test 2023
Stage 2: train 2022-2023  -> test 2024
Stage 3: train 2022-2024  -> test 2025
```

The final OOS result stitches together only test periods.

Current limitation:

- FDM is trained honestly per stage.
- The universe is still selected once before the run using the full requested window.
- Next honesty fix: move universe selection into the OOS stage loop.

## Portfolio Gap Investigation

The generated report showed a flat section in the middle of the chart.

Initial suspicion:

- Portfolio aggregation uses inner join:

```python
returns = pd.concat(return_columns, axis=1, join="inner").sort_index()
```

So the portfolio has a row only when **every selected ticker** has a return on that date.

ETLN was found to have a real trading gap:

- MOEX suspended Etalon (`ETLN`) trading from **2 July 2025**
- Trading resumed on **8 September 2025**
- Reason: redomiciliation and conversion of GDRs into ordinary shares

Sources found:

- Etalon official release: `https://www.etalongroup.com/news/mkpao-etalon-grup-obyavlyaet-o-vozobnovlenii-torgov-aktsiyami-na-moskovskoy-birzhe/`
- Forbes article on trading halt from 2 July: `https://www.forbes.ru/investicii/540286-mosbirza-ostanovit-torgi-depozitarnymi-raspiskami-etalona-so-2-iula`

Conclusion:

- ETLN missing data from July to early September is expected.
- `load-klines` cannot fill that gap because there were no exchange trades.
- Current universe coverage filter checks total kline count, but not internal gaps.

## Next Fix

Add a universe filter to exclude tickers with large internal kline gaps.

Proposed rule:

```text
exclude share if max internal kline gap > 7 or 10 calendar days
```

Likely places:

- `TinvestRepository`: SQL method to compute max internal gap by `ticker_id`
- `InstrumentsService.filter_shares(...)`: apply after count coverage
- `framework.backtest.__main__`: keep using `filter_shares(...)`

Suggested SQL shape:

```sql
WITH ordered AS (
    SELECT
        ticker_id,
        k_interval,
        LAG(k_interval) OVER (
            PARTITION BY ticker_id
            ORDER BY k_interval
        ) AS prev_interval
    FROM backtests.kline_1d
    WHERE k_interval >= :start_dt
      AND k_interval < :end_dt
)
SELECT
    ticker_id,
    MAX(k_interval - prev_interval) AS max_gap
FROM ordered
WHERE prev_interval IS NOT NULL
GROUP BY ticker_id;
```

Then drop instruments whose `max_gap` is above the threshold.
